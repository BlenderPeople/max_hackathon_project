# MAX Заказы (Команда: Лунные сапоги)

## Назначение решения
Данное MVP Mini App предназначено для организации процесса заказа услуг внутри экосистемы MAX. Клиент может открывать карточку услуги (например, по диплинку), оформлять заказ с выбором времени, а мастер (владелец бизнеса) может принимать, оценивать и вести заказ по этапам, отправляя подтверждения и уведомления клиенту через бота MAX.

## Основной пользовательский сценарий
1. Клиент переходит в профиль мастера или открывает услугу по диплинку.
2. Клиент создает заказ: выбирает желаемое время, дату и описывает задачу.
3. Мастер получает уведомление в боте, заходит в свой профиль и видит новый заказ.
4. Мастер проводит осмотр/оценку и отправляет цену на согласование клиенту.
5. Клиент получает уведомление, заходит в приложение и согласует цену.
6. Мастер поэтапно выполняет услугу, отмечает выполнение этапов и завершает заказ. Клиент видит прогресс в реальном времени.

## Состав и архитектура решения
Решение состоит из следующих компонентов:
- **Frontend (Mini App)**: React 18, TypeScript, Vite, TanStack Query. Обеспечивает пользовательский интерфейс внутри платформы MAX.
- **Backend (API)**: Python 3.12, FastAPI, SQLAlchemy 2. Обрабатывает логику заказов, профилей, услуг и интеграцию с API MAX.
- **Database**: PostgreSQL 16. Хранит информацию о пользователях, заказах, услугах и файлах.
- **Интеграции**: MAX Bridge, MAX Bot HTTP API, обработка Webhook событий.

## Команда для запуска всех локальных компонентов через Docker
Для запуска всего проекта одной командой используйте:
```bash
docker compose up --build
```
*(Либо `docker-compose up --build`, если у вас установлена старая версия docker-compose)*

## Необходимые параметры окружения
Проект требует файл `.env` в корневой директории для настройки. Вы можете создать его из готового шаблона без рабочих ключей:
```bash
cp .env.example .env
```
(В PowerShell: `Copy-Item .env.example .env`)

## Переменные окружения
Пример переменных в `.env`:
- `MAX_BOT_TOKEN`: Уникальный токен бота MAX (обязателен для интеграции, выдается платформой). Без него приложение может работать в изолированном режиме на моках.
- `POSTGRES_USER`: Пользователь БД.
- `POSTGRES_PASSWORD`: Пароль БД.
- `POSTGRES_DB`: Имя БД.
- `DATABASE_URL`: Строка подключения для SQLAlchemy (например, `postgresql+asyncpg://user:pass@db:5432/dbname`).
- `VITE_API_MODE`: Установите `real` для работы с бэкендом (если оставить пустым, UI может работать в режиме моков для UI-тестирования).

## Используемые порты
- **Фронтенд (Vite)**: `5173` (доступен по http://localhost:5173)
- **Бэкенд (FastAPI)**: `8000` (доступен по http://localhost:8000/api/docs)
- **База данных (PostgreSQL)**: `5432`

## Зависимости
- Backend: библиотеки зафиксированы в `pyproject.toml` (FastAPI, SQLAlchemy, asyncpg, pydantic, alembic).
- Frontend: библиотеки и их версии зафиксированы в `frontend/package.json` и `frontend/package-lock.json` (react, react-dom, react-router-dom, @tanstack/react-query).

## Внешние сервисы и интеграции
Для полной функциональности решения необходим **сервис экосистемы MAX**:
- **MAX Bot HTTP API и Webhook**: Необходим для аутентификации (проверки `initData`) и отправки push-уведомлений между мастером и клиентом. 
*Важно:* Локально (внутри Docker) воспроизвести сервер авторизации MAX невозможно. Для полноценного тестирования реальной авторизации и уведомлений необходимо прокинуть туннель (например, ngrok) до вашего локального порта `8000` и указать этот HTTPS URL в настройках Webhook бота в кабинете MAX, а также передать валидный `MAX_BOT_TOKEN` в `.env`. Без этого можно тестировать Frontend-часть в режиме демо-моков, которая остается доступной для прохождения основного сценария.

## Описание работы с данными
- Все данные (заказы, пользователи, услуги) хранятся в реляционной базе PostgreSQL.
- Миграции схемы БД выполняются автоматически при старте бэкенда с помощью Alembic.
- Используются "непрозрачные" токены (`public_token`) вместо инкрементальных ID для защиты от перебора (IDOR).
- Файлы заказов (фото/документы) сохраняются в приватный Docker Volume и отдаются строго участникам заказа по токену сессии.

## Порядок работы с тестовыми данными
При первом запуске Docker контейнеров (когда база пуста), бэкенд автоматически создает демо-данные (seed):
- Тестовый мастер и его бизнес-профиль.
- Набор тестовых услуг.
- Несколько готовых тестовых заказов в разных статусах (новые, ожидающие согласования, завершенные).
Повторные запуски контейнера не удаляют данные. Если вы хотите сбросить базу и заново заполнить её тестовыми данными, удалите Docker Volume базы данных:
```bash
docker compose down -v
```

## Пошаговый сценарий проверки
1. Установите `.env` файл из `.env.example`.
2. Запустите `docker compose up --build`. Сборка занимает менее 5 минут (в зависимости от скорости загрузки базовых образов Python/Node).
3. Откройте `http://localhost:5173` в браузере.
4. Перейдите в раздел "Мои услуги" и создайте новую услугу, либо используйте существующую.
5. Выберите услугу и нажмите "Создать заказ", укажите дату и описание (или используйте публичную ссылку на профиль/услугу для симуляции клиента).
6. Перейдите в расписание или в список заказов, откройте созданный заказ.
7. Как мастер, нажмите "Указать стоимость" и введите итоговую сумму.
8. Заказ перейдет в статус "Ожидает согласования клиента".

## Примеры ожидаемого поведения системы
- При попытке клиента отредактировать заказ после того, как мастер уже выставил цену, система запрещает изменения (кнопки редактирования скрываются).
- При переходе на "свободный слот" в календаре, время в форме заказа автоматически предзаполняется выбранным таймслотом.
- Если у мастера не настроено расписание, создание заказа на недоступные дни блокируется.

## Известные ограничения
- Отсутствует интеграция с реальными платёжными шлюзами (оплата переводится по договоренности и отмечается мастером в приложении вручную).
- Загрузка файлов ограничена размером 10 МБ и данные хранятся локально в Docker Volume (не в S3 облаке).
- Вне среды Telegram/MAX аутентификация симулируется для обеспечения возможности тестирования UI.

## Порядок остановки и повторного запуска решения
Остановка всех контейнеров **без потери данных** в БД:
```bash
docker compose down
```
Повторный запуск:
```bash
docker compose up
```
Для полной очистки (с удалением БД и сбросом демо-данных) добавьте флаг `-v`:
```bash
docker compose down -v
```
