# MAX Заказ — план хакатонного MVP

Дата фиксации плана: 20 сентября 2026.

## 1. Решение по продукту

Продукт — не маркетплейс и не CRM. Это лёгкий кабинет заказа внутри MAX для самозанятого/ИП и его клиента.

Главная сущность — **заказ**. Карточка услуги и профиль мастера нужны как короткий вход в создание заказа, а не как самостоятельная торговая площадка.

Ценность MVP:

> Клиент переходит по ссылке на услугу, создаёт заказ, мастер получает уведомление, ведёт заказ по этапам, а клиент всегда видит статус, цену, подтверждения, оплаты, файлы и историю.

Один MAX-пользователь может одновременно быть клиентом и мастером. Отдельного переключателя ролей нет: доступные действия определяются отношением пользователя к конкретному заказу.

## 2. Главный демонстрационный сценарий

1. Мастер заранее создал услугу «Обрезка деревьев» с фото, описанием и ценой «от 5 000 ₽».
2. Клиент открывает внешний диплинк `https://max.ru/<botName>?startapp=service_<opaque-token>`.
3. Mini App показывает карточку услуги и профиль мастера.
4. Клиент нажимает «Заказать», добавляет короткое описание и желаемый срок.
5. Создаётся заказ со статусом «Новый», мастер получает сообщение от бота с кнопкой открытия заказа.
6. Мастер открывает заказ, задаёт итоговую цену и переводит его в «Согласование».
7. Клиент получает уведомление и подтверждает цену/работу.
8. Мастер переводит заказ в «В работе», затем «Готов»; клиент видит timeline и получает уведомления.
9. Дополнительно в демо: мастер фиксирует предоплату, обе стороны видят остаток; клиент скачивает приложенный файл.

Этот вертикальный сценарий должен работать целиком раньше, чем команда добавляет второстепенные экраны.

## 3. Состав MVP

### Обязательно

- авторизация через подписанные `window.WebApp.initData`;
- единый пользовательский профиль MAX;
- минимальный профиль мастера;
- создание и редактирование одной или нескольких карточек услуг;
- открытие услуги и заказа по безопасному диплинку;
- создание заказа клиентом и мастером;
- список заказов с режимами «Все», «Требуют внимания», «В работе», «Просрочены», «Завершены»;
- карточка заказа с разным набором действий для клиента и мастера;
- этапы заказа и автоматическая история изменений;
- запрос подтверждения и действия «Подтвердить/Отклонить»;
- ручной учёт оплат без эквайринга;
- файлы заказа: загрузить, посмотреть метаданные, скачать;
- уведомления от бота о новом заказе, подтверждении и смене этапа;
- завершение заказа;
- адаптивный интерфейс, светлая/тёмная тема и состояния loading/empty/error.

### Если основной сценарий уже стабилен

- публичная страница мастера со списком его услуг;
- простой поиск услуг по названию и категории;
- отраслевые шаблоны этапов;
- «Повторить заказ»;
- QR-код диплинка;
- гарантия завершённого заказа.

### После хакатона

- глобальный маркетплейс и ранжирование;
- отзывы и модерация отзывов;
- внутренний мессенджер;
- отдельный чат на каждый товар/заказ;
- онлайн-оплата и чеки;
- сотрудники и сложные права;
- рекомендации, AI, CRM-интеграции и аналитика.

## 4. Навигация и экраны

Нижняя навигация MVP:

1. **Заказы** — основной экран, фильтры и «Требуют внимания».
2. **Услуги** — карточки услуг мастера; для клиента — простой поиск, если успеваем.
3. **Профиль** — данные пользователя/мастера и настройки.

Отдельный экран «События» в MVP не нужен: события конкретного заказа показываются в его timeline, а внешние уведомления приходят через бота.

Кнопка `+` открывает контекстное действие:

- мастеру — «Новый заказ» или «Новая услуга»;
- клиенту — поиск/выбор услуги.

Минимальный набор экранов после сокращения frontend-объёма:

- запуск/авторизация;
- список заказов;
- одна переиспользуемая карточка заказа с действиями по правам пользователя;
- единая форма создания/редактирования заказа;
- карточка услуги с короткой формой заказа;
- единая форма создания/редактирования услуги;
- минимальный профиль мастера/пользователя;
- модальные формы подтверждения и оплаты внутри карточки заказа;
- файлы и timeline как секции карточки заказа, а не отдельные экраны.

Чат внутри Mini App не создаём. Действие «Обсудить в MAX» открывает нативный контекст MAX, а значимые договорённости фиксируются отдельным подтверждением или событием заказа.

## 5. Технологический контур

### Frontend

- TypeScript, React 18+, Vite;
- `@maxhub/max-ui` для основных компонентов и тем;
- MAX Bridge через `max-web-app.js`;
- React Router;
- TanStack Query для серверного состояния;
- обычный React state для локальных форм; отдельный глобальный store в MVP не нужен.

### Backend

- Python 3.12;
- FastAPI;
- SQLAlchemy 2 + Alembic;
- PostgreSQL;
- Pydantic Settings;
- `httpx` для вызовов MAX Bot API;
- S3-совместимое хранилище для файлов либо локальное объектное хранилище в демо-окружении.

Официальная документация предлагает библиотеки ботов для JavaScript и Go, поэтому Python-интеграцию строим поверх документированного HTTP API, не завязываясь на неофициальный SDK.

### Инфраструктура

- один HTTPS-домен;
- `/` — собранный Mini App;
- `/api/*` — FastAPI;
- `/webhooks/max` — webhook бота;
- доверенный сертификат Минцифры добавляется в CA bundle приложения и контейнера; TLS-проверка не отключается через `-k`/`verify=False`;
- секреты только в переменных окружения;
- токен бота никогда не попадает во frontend;
- healthcheck, структурированные логи, seed демо-данных.

## 6. Архитектура потока

```text
MAX client
  ├─ Mini App (React + MAX UI + Bridge)
  │    └─ HTTPS /api
  │          └─ FastAPI ── PostgreSQL
  │                    ├── Object Storage
  │                    └── MAX Bot API
  └─ Bot dialog
       └─ HTTPS webhook ── FastAPI
```

Критические правила:

- backend валидирует `initData` по HMAC и проверяет свежесть `auth_date`;
- frontend не доверяет `initDataUnsafe` для авторизации;
- права проверяются на каждом endpoint по владельцу бизнеса и участникам заказа;
- в диплинк кладётся непрозрачный токен/публичный идентификатор, а не персональные данные;
- webhook проверяет `X-Max-Bot-Api-Secret`;
- обработка webhook идемпотентна, потому что MAX повторяет доставку;
- уведомление отправляется только после успешной фиксации изменения заказа.

## 7. Минимальная модель данных

### Таблицы

- `users`: `id`, `max_user_id`, имя, username, avatar, timestamps;
- `businesses`: `id`, `owner_id`, название, описание, контакты;
- `services`: `id`, `business_id`, title, description, price_from, image_key, is_active, public_token;
- `orders`: `id`, `public_token`, `business_id`, `service_id?`, `customer_id`, title, description, price, due_at, status, current_stage_id, created_at, completed_at;
- `order_stages`: `id`, `order_id`, position, title, state, completed_at;
- `approvals`: `id`, `order_id`, `author_id`, title, description, price_delta, status, decided_by, decided_at;
- `payments`: `id`, `order_id`, amount, comment, recorded_by, paid_at;
- `files`: `id`, `order_id`, storage_key, filename, content_type, size, uploaded_by, created_at;
- `order_events`: `id`, `order_id`, actor_id?, type, payload_json, created_at;
- `notification_outbox`: `id`, `user_id`, order_id?, type, payload_json, status, attempts, created_at`.

`order_events` — источник timeline. «Требует внимания» вычисляется из просрочки и незакрытых подтверждений; отдельную CRM-сущность для этого не создаём.

### Базовые состояния

- заказ API: `new`, `approval`, `in_progress`, `done`;
- этап: `pending`, `current`, `done`;
- подтверждение: `pending`, `approved`, `rejected`.

## 8. API-контракт первого релиза

### Сессия

- `POST /api/auth/max` — проверить `initData`, создать/обновить пользователя, вернуть короткую сессию;
- `GET /api/me` — текущий пользователь и его возможности.

### Услуги и мастер

- `GET /api/services/{public_token}`;
- `GET /api/businesses/{public_token}`;
- `GET /api/businesses/{public_token}/services`;
- `POST /api/services`;
- `PATCH /api/services/{public_token}`.

### Заказы

- `GET /api/orders?filter=attention|active|overdue|completed`;
- `POST /api/orders`;
- `GET /api/orders/{public_token}`;
- `PATCH /api/orders/{public_token}`;
- `POST /api/orders/{public_token}/stages/{stage_token}/activate`;
- `POST /api/orders/{public_token}/complete`;
- `GET /api/orders/{public_token}/events`.

### Подтверждения, оплаты, файлы

- `POST /api/orders/{public_token}/approvals`;
- `POST /api/approvals/{approval_token}/decision`;
- `POST /api/orders/{public_token}/payments`;
- `POST /api/orders/{public_token}/files`;
- `GET /api/files/{file_token}/download`.

### MAX

- `POST /webhooks/max`;
- внутренний сервис `MaxBotClient.send_message(...)`;
- генератор диплинков для `service_<token>` и `order_<token>`.

Выданный организаторами бот проверен через `GET /me`:

- `bot_id`: `80705059`;
- `username`: `t216_hakaton_bot`;
- название: «Хакатон 216»;
- базовый диплинк после привязки Mini App: `https://max.ru/t216_hakaton_bot?startapp=<payload>`;
- токен является рабочим Bot API token и хранится только вне Git.

Сначала команда согласует JSON-примеры этих endpoint'ов и мок-ответы. Это позволяет frontend и backend идти параллельно.

- репетиция демо на production-like окружении.

### Этап 5 — только при наличии запаса

- поиск услуг;
- шаблоны этапов;
- QR и повтор заказа;
- визуальные улучшения.

## 12. Definition of Done MVP

- новый пользователь открывает Mini App из диплинка без ручного логина;
- чужой пользователь не может увидеть или изменить заказ;
- заказ создаётся из карточки услуги не более чем за три коротких шага;
- мастер получает уведомление и открывает нужный заказ одной кнопкой;
- клиент видит актуальный этап, цену, оплату, файлы и timeline;
- подтверждение сохраняет автора, решение и время;
- смена этапа создаёт событие и уведомление;
- повторный webhook не создаёт дублей;
- все секреты находятся только на backend;
- основной сценарий проверен минимум на одном мобильном клиенте MAX и в web-клиенте;
- demo seed и короткий сценарий презентации воспроизводятся без ручного ремонта БД.

## 13. Основные риски

1. **Привязка Mini App.** Хакатонный Bot API token успешно проверен, бот `t216_hakaton_bot` доступен. Оставшийся внешний шаг — развернуть HTTPS-версию Mini App и вовремя отправить URL через форму организаторов.
2. **Попытка построить маркетплейс.** Каталог, отзывы и умный поиск режутся первыми.
3. **Второй мессенджер внутри MAX.** В MVP не делаем; договорённости фиксируем через approvals и timeline.
4. **Недоверенная авторизация.** `initDataUnsafe` подходит для отображения, но не для backend auth; подпись проверяет сервер.
5. **Webhook-дубли и задержки.** Обработчики идемпотентны, endpoint быстро отвечает 200, тяжёлая работа выполняется после приёма события.
6. **Файлы.** Проверять лимиты, MIME/размер, выдавать временные HTTPS-ссылки и скачивать через Bridge.
7. **Размытые роли.** Возможности зависят от конкретного заказа, а не от глобального взаимоисключающего флага «клиент/продавец».
