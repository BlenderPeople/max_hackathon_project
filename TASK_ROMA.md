# Рома — UI и продуктовый frontend owner

## Цель роли

Быстро собрать цельный адаптивный интерфейс Mini App, в котором клиент создаёт заказ из услуги, а клиент и мастер видят одну карточку с разными доступными действиями. UI обязан работать на согласованных моках до готовности backend.

## Результат первого вертикального среза (к вечеру 22 сентября)

- интерфейс проходит путь: карточка услуги → короткая форма заказа → карточка заказа;
- у клиента и мастера различаются действия, но используется одна переиспользуемая карточка;
- есть аккуратные loading, empty и error состояния, нижняя навигация, светлая/тёмная тема и mobile layout;
- моки совпадают с OpenAPI/JSON-примерами Сергея, поэтому Василий подключает реальный API без переписывания компонентов.

## Зона владения

- React/Vite, маршруты и layout экранов;
- MAX UI, theme tokens, нижняя навигация, адаптивность;
- визуальные компоненты списка, услуги, заказа, timeline, forms, approvals, payment, files, profile;
- UI-моки строго по контракту, accessibility и финальный polish.

Не реализуй MAX Bridge, авторизацию, сетевой клиент, диплинки, webhook, storage или deploy: это зона Василия. Не меняй предметные статусы и payload API без Сергея.

## Экранная карта MVP

1. Запуск/авторизация: нейтральный loading и понятная ошибка запуска.
2. Заказы: фильтры «Все», «Требуют внимания», «В работе», «Просрочены», «Завершены».
3. Карточка заказа: статус, цена, остаток, доступные действия по роли, timeline, files.
4. Услуга: фото, описание, цена «от», профиль мастера, CTA «Заказать».
5. Форма заказа: описание и желаемый срок — не больше трёх коротких шагов от услуги до создания.
6. Профиль/услуги мастера: минимум, нужный для demo.

Отдельного чата и экрана «События» не делаем: обсуждение открывается в MAX, история остаётся внутри карточки заказа.

## Стартовые задачи

1. Согласуй с Сергеем TypeScript-представления ответов и состояния экранов; используй реальные `public_token`, не выдумывай параллельные id.
2. Собери app shell: theme, bottom navigation, shared feedback states и responsive constraints.
3. Сделай компоненты сначала на mocks: `ServiceCard`, `OrderCard`, `OrderTimeline`, `CreateOrderForm`, `ApprovalDialog`, `PaymentDialog`, `FileList`.
4. В order view принимай с сервера `available_actions`; не выводи права из клиентской «роли» самостоятельно.
5. Передавай Василию готовые экранные компоненты и список нужных query/input типов; он подключает Bridge и typed API client.

## Критерии приёмки

- [ ] Интерфейс работает на согласованных моках и не зависит от готовности backend.
- [ ] Один order view корректно показывает действия клиента и мастера.
- [ ] Пользователь видит текущий этап, цену, оплаты, файлы и историю.
- [ ] Создание заказа из услуги укладывается в три коротких шага.
- [ ] Состояния loading/empty/error не являются пустыми экранами.
- [ ] Все ключевые экраны проверены на узком мобильном viewport.
