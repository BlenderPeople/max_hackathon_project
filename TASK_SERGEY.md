# Сергей — Backend/domain и product owner

## Цель роли

Владеть бизнесовой моделью и API MVP: пользователь, бизнес, услуга, заказ, этапы, approvals, платежи, права и история. Ваш результат должен позволить Роме делать UI по стабильному контракту, а Василию — доставлять уведомления и деплоить приложение без вмешательства в доменную логику.

## Результат первого вертикального среза (к вечеру 22 сентября)

- проверяется подписанный MAX `initData`, создаётся/обновляется пользователь и выдаётся короткая сессия;
- есть миграции и seed: мастер, клиент, бизнес, услуга «Обрезка деревьев», заказ;
- frontend может получить услугу, создать заказ, открыть его обеими сторонами и изменить этап по правилам;
- OpenAPI и JSON-примеры для ключевых ручек согласованы до массовой разработки UI.

## Зона владения

- FastAPI, PostgreSQL, SQLAlchemy 2, Alembic, Pydantic Settings;
- модели `users`, `businesses`, `services`, `orders`, `order_stages`, `approvals`, `payments`, `order_files`, `order_events`;
- HMAC-проверка `initData`, сессия и проверка прав на каждом endpoint;
- use cases, статусы, timeline, фильтры attention/active/overdue/completed;
- тесты бизнес-правил, OpenAPI, seed и решения по MVP-scope.

Василий владеет adapter'ами MAX, webhook, файлами, outbox, окружениями и deploy. Не добавляй это в свой контур без синхронизации.

## Стартовые задачи

1. Зафиксируй user stories и Definition of Done из `PLAN.md` как короткий backlog с приоритетом: вертикальный сценарий, затем approvals/stages, затем payments/files.
2. Опиши ER-модель и статусы заказа. Обязательные переходы: `new` → `approval` → `in_progress` → `done`; отмена/просрочка — только если нужны UI и demo.
3. До кодинга опубликуй OpenAPI/JSON для `POST /api/auth/max`, `GET /api/me`, услуги и ключевых операций заказа.
4. Создай миграции и idempotent seed. Схему БД меняешь ты; Василий согласует с тобой любые дополнительные таблицы.

## API первого среза

- `POST /api/auth/max`;
- `GET /api/me`;
- `GET /api/services/{public_token}`;
- `POST /api/orders`;
- `GET /api/orders/{public_token}`;
- `PATCH /api/orders/{id}`;
- `POST /api/orders/{id}/stages/{stage_id}/activate`;
- `GET /api/orders/{id}/events`.

Наружные идентификаторы — непрозрачные `public_token`, не персональные данные и не последовательные database id. Возвращай в карточке заказа его участников, доступные текущему пользователю действия, цену, этап, approvals/payments/files и timeline в форме, удобной для экрана.
